# CodeLearn - MVP Technical Specification v0.3

**Local-first Code Change Learning Viewer**

- Version: 0.3.0
- Status: Ready for Implementation
- Type: Open-source Developer Tool
- Backend: Go
- Frontend: React + TypeScript
- Interface: CLI + Local Web Viewer + Optional Agent Skill
- AI Integration: External Agent, No Direct LLM API

> **Amendment to v0.3.** Sections 2.2, 6.1, 6.2 and instruction 8 originally
> defined the change unit as the raw git diff hunk and excluded symbol level
> analysis. That decision was reversed by the maintainer: a hunk is an
> arbitrary grouping that can span several functions, and a new file is a
> single hunk covering everything, which makes a poor unit to learn from.
> CodeLearn now cuts changes along symbol boundaries where it can outline the
> file, and falls back to hunks where it cannot. Those sections below reflect
> the amended decision; everything else is unchanged.

# 1. Project Overview

## 1.1 Background

As LLM-based coding agents spread, developers increasingly have to understand
and review code they did not write themselves.

A git diff viewer compares changed code, but the explanation needed to learn
how the new implementation works has to be produced separately. Microsoft
CodeTour connects explanations to code locations and lets a reader step
through them.

CodeLearn combines both, so local changes can be compared and learned before a
commit or a pull request exists.

## 1.2 Project Goal

> Provide a lightweight, local-first interface for understanding git code
> changes through side-by-side diffs and code-anchored learning explanations.

The user runs:

```bash
codelearn .
```

CodeLearn starts a local web server and shows the current repository's changes
in a browser. Optionally it imports explanations generated by an external
coding agent such as Claude Code or Codex and attaches them to the code.

## 1.3 Core Principles

**Local-first.** Git analysis, diff rendering and explanation storage all run
locally.

**Pre-commit first.** The default subject is the working tree, with no commit
or pull request required.

**Agent-independent.** CodeLearn Core depends on no particular coding agent.

**Learning-oriented.** The goal is understanding changed code, not fixing it
or finding bugs.

**Minimal MVP.** Collect git changes, render diffs and attach explanations
correctly, rather than adding features.

# 5. Git Change Collection

## 5.1 Repository Detection

```bash
git rev-parse --show-toplevel
```

The returned path is the repository root. A path that is not inside a
repository makes the CLI print an error and exit.

## 5.2 Comparison Model

```text
Base:   HEAD
Target: Current working tree + staged changes + untracked files
```

The comparison is between the file state at HEAD and the final state the user
sees. Changes that exist only in the index must still be reflected. In
particular, a file staged and then deleted from the working tree must not be
judged by working tree existence alone.

A file whose change exists *only* in the index - staged, then reverted on
disk - produces no HEAD-to-working-tree difference at all. It is therefore
detected from porcelain status, flagged `index_only`, and compared against the
index rather than the working tree, so the staged change is visible without
breaking the "one final state" model for every other file.

## 5.3 Git Commands

```bash
git status --porcelain=v1 -z --untracked-files=all
git diff HEAD --no-ext-diff --no-textconv --no-color
git ls-files --others --exclude-standard -z
```

These are the available tools, not a requirement to concatenate separate diff
outputs. Staged and unstaged changes must be merged without duplication and
must match the final file state.

Paths use NUL-separated output. User-supplied paths are never interpolated
into a shell string. Git commands run through `exec.CommandContext`.

## 5.4 Supported Change Types

| Change Type | Required |
|---|---|
| Modified | Yes |
| Added | Yes |
| Deleted | Yes |
| Untracked | Yes |
| Staged | Yes |
| Unstaged | Yes |
| Renamed | Best effort |
| Binary | Metadata only |

Untracked files are new files with an empty Before. Renames detected by git
keep both paths. Binary files are not passed to the diff viewer. Submodules
show their change status only.

## 5.5 Snapshot Consistency

A change snapshot represents one point in time: git state, file contents and
change units must agree with each other. If a consistent result cannot be
produced because files changed during collection, retry or ask the user to
refresh. Export, import and the web viewer all use the same snapshot id.

# 6. Change Unit Model

## 6.1 Unit Definition *(amended)*

A change unit is the smallest region a reader would name.

Git hunks drive *detection* - they are what reports that a file changed and
where. Where CodeLearn can produce a symbol outline for a file, the change is
cut along symbol boundaries instead, so one unit is one function, method or
class. Code outside any symbol - imports, constants, top level statements -
becomes a `module level` unit. A symbol whose text is unchanged produces no
unit.

Outlines are produced without a parser dependency:

| Language | Mechanism |
|---|---|
| Go | source scanning for `func`, `type`, methods |
| Python | indentation-aware scanning for `def` and `class` |
| TypeScript, JavaScript, TSX, JSX | brace matching for functions, arrow consts, classes, methods, types |
| C, C++, Java, C#, Rust, Swift, Kotlin | brace matching for functions, classes, methods |
| anything else | no outline; the raw hunk is the unit |

A unit covers the whole symbol, not only the edited lines, so a one-line
change is read in the context of the function it lives in.

```json
{
  "id": "sha256:example-change-id",
  "file": "internal/git/diff.go",
  "symbol": "Collect",
  "kind": "function",
  "label": "Collect()",
  "old_range": { "start": 20, "count": 9 },
  "new_range": { "start": 20, "count": 16 },
  "before": "old code",
  "after": "new code"
}
```

A `count` of 0 marks an insertion or deletion with no lines on that side.
`symbol` is null and `kind` is `block` for module level and hunk fallback
units.

## 6.2 Change ID *(amended)*

A change id is the SHA-256 of a normalised serialisation of:

- Base commit
- File path
- Symbol name (empty for module level and hunk units)
- Before code
- After code
- An occurrence index, non-zero only for units that are otherwise identical

Line ranges are deliberately excluded. Including them would tie every id to
all the code above it in its file, so inserting one import would invalidate
the explanations of every unit below it even though none of that code
changed.

The same snapshot always produces the same change id. Changing the code or its
location changes the id. That is intended in the MVP: an id that survives is
proof the code behind it is unchanged.

## 6.3 Snapshot ID

The snapshot id is derived from:

- Base commit
- Changed file list and statuses
- Final contents of the changed files
- Change unit data

A canonical serialisation is used, so neither file ordering nor JSON key
ordering may affect the result.

# 7. CLI Specification

## 7.1 Commands

```bash
codelearn                            # open the current repository
codelearn /path/to/repository        # open a specific repository
codelearn . --no-browser             # do not launch a browser
codelearn export --output changes.json
codelearn import analysis.json
```

## 7.2 CLI Behavior

`codelearn .` detects the repository, identifies its root, builds an initial
snapshot, starts a local HTTP server on an available port, launches the
browser, and serves until stopped.

```text
CodeLearn v0.3.0

Repository: /home/user/project
Branch: main
Changed Files: 5

Viewer: http://127.0.0.1:8765

Press Ctrl+C to stop.
```

## 7.3 Runtime Behavior

- Binds `127.0.0.1`
- Uses an available port assigned by the OS
- Shuts down on SIGINT / SIGTERM
- Prints the URL when the browser cannot be launched
- Reports git errors in human terms
- Never modifies repository files

The browser launch and the HTTP server are managed by the same CLI process.

# 8. Backend API Specification

## 8.1 GET /api/repository

```json
{
  "name": "my-project",
  "branch": "main",
  "base_commit": "abc123",
  "snapshot_id": "sha256:example",
  "changed_files": 3
}
```

## 8.2 GET /api/changes

```json
{
  "snapshot_id": "sha256:example",
  "files": [
    {
      "path": "internal/git/diff.go",
      "status": "modified",
      "additions": 32,
      "deletions": 14,
      "change_ids": ["sha256:change-a", "sha256:change-b"]
    }
  ]
}
```

## 8.3 GET /api/files/diff?path=...

```json
{
  "snapshot_id": "sha256:example",
  "path": "internal/git/diff.go",
  "before": "original file content",
  "after": "modified file content",
  "changes": [
    {
      "id": "sha256:change-a",
      "symbol": "Collect",
      "kind": "function",
      "label": "Collect()",
      "old_range": { "start": 20, "count": 9 },
      "new_range": { "start": 20, "count": 16 }
    }
  ]
}
```

The path is validated against the changed file list of the current snapshot.
A client-supplied path is never read from the filesystem directly.

## 8.4 GET /api/analysis

```json
{
  "snapshot_id": "sha256:example",
  "steps": [
    {
      "change_id": "sha256:change-a",
      "title": "Cache allocation",
      "what": "...",
      "how": "...",
      "why": "..."
    }
  ]
}
```

With no valid analysis, `steps` is an empty array.

## 8.5 POST /api/refresh

Re-reads git state and builds a new snapshot. Read endpoints serve the
snapshot the server currently holds, so this is the only thing that picks up
edits: one screen costs one collection, and the panes cannot disagree about
which state they show.

```json
{ "snapshot_id": "sha256:new-snapshot", "changed_files": 4 }
```

Explanations from an earlier snapshot must never be attached to new changes.

## 8.6 API Security

- Binds the loopback interface only
- Validates file paths against the snapshot
- Limits HTTP request size
- Accesses the repository read-only
- Validates `Origin` on state-changing requests
- Prevents external web pages from calling the local API
- Offers no option to expose the API externally

# 9. Frontend Specification

## 9.1 Layout

```text
+----------------------------------------------------------------+
| CodeLearn                            Repository: my-project     |
+----------------+----------------------------+------------------+
| Changed Files  |       Diff Viewer          | Learning Guide   |
|                |                            |                  |
| cache.go       | Before        After        | Step 1 / 3       |
| scheduler.go   |                            |                  |
| config.go      | Old Code      New Code     | What             |
|                |                            | How              |
|                | [Selected Change Unit]     | Why              |
|                |                            | Previous / Next  |
+----------------+----------------------------+------------------+
```

## 9.2 React Components

**FileList** - changed file list, per-file status, added and deleted line
counts, selection events.

**DiffViewer** - Monaco diff editor, Before/After rendering, change unit
positions, highlighting the selected unit, selection events, scrolling to the
code of the active learning step.

Monaco's own diff output is never used to generate change ids; the backend
snapshot is the authority for ids and code locations.

**LearningPanel** - the steps for the selected file, What / How / Why,
Previous / Next, an empty state, and Markdown rendering. Markdown is rendered
with raw HTML disabled.

## 9.3 Frontend State

```typescript
type AppState = {
  snapshotId: string | null;
  selectedFile: string | null;
  selectedChangeId: string | null;
  activeStepIndex: number;
};
```

Repository, diff and analysis data are each loaded from their own API. Only
React hooks are used in the initial version.

## 9.4 Performance Requirements

- The file list and per-file diff data load separately
- Only the selected file's code reaches Monaco
- Monaco is lazy loaded
- Stale responses from superseded requests are ignored
- Analysis results are reused within one snapshot
- Oversized files are not rendered; a notice is shown instead
- Monaco editor instances are disposed properly

A file whose Before or After text exceeds 2 MiB shows a size notice instead of
a diff. The limit is a constant; no user-facing setting in the MVP.

# 10. Shared Skill Specification

## 10.1 Purpose

The shared skill analyses the change units CodeLearn exports and generates
learning explanations. It is a document defining a procedure and an output
format for a compatible coding agent, not code that calls an LLM API.

## 10.2 Skill Workflow

```text
1. Detect repository
2. Execute codelearn export
3. Read change units
4. Inspect necessary context
5. Generate What / How / Why
6. Generate analysis JSON
7. Execute codelearn import
8. Report result
```

## 10.3 Explanation Requirements

**What** - the difference between the old and new implementation of this unit,
and what the new behaviour is.

**How** - the order of operations, key conditions, data flow, and the core
implementation mechanism.

**Why** - why it is implemented this way: the alternative it avoids, the edge
case it guards, the constraint it satisfies. Evidence must come from the code;
an inference must be marked as one, and may be omitted entirely.

## 10.4 Analysis JSON

```json
{
  "schema_version": "1.0",
  "snapshot_id": "sha256:example",
  "steps": [
    {
      "change_id": "sha256:change-a",
      "title": "Cache reuse",
      "what": "Cache creation was replaced with reuse.",
      "how": "The existing cache object is returned.",
      "why": "Avoids paying the construction cost on every call."
    }
  ]
}
```

`why` is optional. `change_id`, `title`, `what` and `how` are required.

## 10.5 Validation

Import validates: JSON parseability, schema version, snapshot id match, change
id validity, duplicate change ids, required fields, and explanation size
limits.

Invalid JSON is not imported. Import is atomic per file: storing only some
steps is not supported in the MVP.

## 10.6 Agent Compatibility

```text
skills/
└── codelearn/
    ├── SKILL.md
    └── references/
        └── analysis-schema.json
```

One shared skill document; per-agent install paths are documented separately.
Analysis logic is never duplicated per agent.

# 11. Analysis Export / Import

## 11.1 Export

```bash
codelearn export --output changes.json
```

Contains schema version, snapshot id, repository metadata, base commit, change
units, Before/After code and code locations. Export never modifies repository
files.

## 11.2 Import

```bash
codelearn import analysis.json
```

Import validates the analysis against the current snapshot. It targets the
git repository of the current working directory by default, and accepts an
explicit repository path.

## 11.3 Local Storage

The OS user cache directory, via `os.UserCacheDir()`:

```text
<user-cache-dir>/
└── codelearn/
    └── <repository-id>/
        └── <snapshot-id>/
            └── analysis.json
```

The repository id is derived from the normalised repository root path. The
analysis file is written to a temporary file and moved into place atomically.
No analysis file is ever created inside the repository.

# 14. Performance Considerations

## 14.1 Backend

Minimise git invocations, apply timeouts, load per-file diff data lazily,
reuse snapshot data, avoid re-analysing whole files unnecessarily, and keep
memory proportional to the number of changed files.

The MVP stays on the git CLI. No git library is adopted before a measurement
shows an actual bottleneck.

## 14.2 Frontend

Lazy Monaco, render only the selected file, avoid needless re-renders, cancel
superseded requests, limit oversized files, keep explanation data separate
from code data.

## 14.3 Performance Evaluation

| Scenario | Measurement |
|---|---|
| 10 changed files | CLI start time |
| 100 changed files | File list response time |
| 1,000 changed files | Snapshot build time |
| 1 MiB source file | Diff render time |
| Repeated refresh | Cache reuse and response time |

These are measurement scenarios, not guaranteed timings. Results are recorded
in the README or a separate benchmark document.

# 15. Testing Strategy

## 15.1 Backend Unit Tests

Go `testing`. Required: repository detection; modified, added, deleted and
untracked files; mixed staged/unstaged; staged then deleted from the working
tree; paths with spaces and special characters; change unit line ranges;
change id determinism; snapshot id determinism; snapshot consistency during
change; analysis JSON validation; snapshot mismatch rejection.

## 15.2 API Tests

`httptest`. Required: repository, changes, file diff, analysis and refresh
APIs; an invalid file path; a snapshot mismatch; a wrong HTTP method; an
oversized request; origin validation.

## 15.3 Frontend Tests

Vitest and React Testing Library. Required: file list rendering, file
selection, diff requests, unit selection, step navigation, the empty state,
selection handling after refresh, and API error handling. Monaco's actual
rendering and scrolling are covered by a browser-based integration check.

## 15.4 End-to-End Scenario

Create a temporary repository, commit, modify files, run `codelearn export`,
verify the export, write a test analysis, run `codelearn import`, start the
viewer, check the files and diffs, check the explanations, modify more code,
refresh, and confirm the previous snapshot's explanations are not misapplied.

The core end-to-end test must run without any LLM.

# 16. Implementation Phases

**Phase 1 - Go CLI & Git Core.** Project init, CLI, repository detection,
change collection, unit extraction, change and snapshot ids, JSON export, unit
tests. *Exit:* accurate change JSON from a real repository.

**Phase 2 - Local Web Viewer.** Go HTTP server, React/Vite project, repository
/ changes / file diff APIs, Monaco, FileList, unit selection, refresh.
*Exit:* `codelearn .` shows uncommitted changes in a browser.

**Phase 3 - Learning Integration.** Analysis schema, import validation, local
storage, analysis API, LearningPanel, CodeTour-style navigation, shared skill
and its documentation. *Exit:* agent-generated explanations are navigable
against real changed code.

**Phase 4 - Packaging & Quality.** Frontend production build, embed
integration, cross-platform build, end-to-end tests, performance
measurements, README, installation guide, licence review. *Exit:* a release
binary runs CodeLearn with no dev server.

# 17. Definition of Done

**CLI** - `codelearn .` runs, detects the repository, starts the server,
launches a browser, and shuts down cleanly.

**Git** - uncommitted changes collected; staged, unstaged and untracked
supported; file list produced; change units identified; snapshot consistent.

**Viewer** - Before/After diff, unit selection, code highlighting, per-file
navigation, refresh.

**Learning** - change export, analysis import, What / How / Why display,
stepwise navigation, code location linking, stale explanations blocked.

**Architecture** - no external LLM API, no agent lock-in, local execution,
repository files untouched, single Go binary distribution.

# 18. Instructions for Coding Agents

1. Implement only the features defined in this document.
2. Use Go for the backend and CLI.
3. Use React and TypeScript for the frontend.
4. Use Monaco Diff Editor for code comparison.
5. Do not integrate external LLM APIs.
6. Do not implement local LLM inference.
7. Keep the shared skill independent from the backend.
8. *(amended)* Use symbol-level change units where a file can be outlined, and
   git diff hunks as the fallback. Outlines must be produced without a parser
   dependency.
9. Use deterministic change ids and snapshot ids.
10. Keep the repository source files read-only.
11. Use the Go standard library wherever practical.
12. Avoid unnecessary abstractions and dependencies.
13. Write tests for each major component.
14. Complete each implementation phase before proceeding.
15. Do not introduce features outside MVP scope without approval.

# 19. Development Constraints

The objective is a working, maintainable MVP, not a feature-rich platform.
Prioritise correct git change representation, reliable diff rendering,
accurate code-to-explanation mapping, simple installation, and a maintainable
architecture.

Do not optimise prematurely. Do not add architectural complexity without a
demonstrated requirement. The project should stay small enough for an
individual open-source maintainer to understand, test and extend.
